1. Introduction
This project designs and implements the backend database for a simplified social media platform, similar in spirit to Twitter or Instagram. The goal is to demonstrate practical database design skills — entity-relationship modeling, normalization, schema creation, and the use of advanced SQL features such as views, triggers, and stored procedures — on a dataset that has realistic, non-trivial relationships (self-referencing follows, many-to-many likes, cascading notifications).
1.1 Objectives
Design a normalized relational schema for a social media application.
Model one-to-many, many-to-many, and self-referencing relationships correctly.
Implement referential integrity using primary and foreign key constraints.
Use triggers to maintain derived data (e.g., like counts) automatically.
Use views and stored procedures to simplify common, repeated queries.
Apply indexing to optimize the queries the application runs most frequently.
Connect the database to a small backend application to demonstrate real usage.
1.2 Scope
The project covers user accounts, posts, comments, likes, follower relationships, and notifications. It intentionally excludes features such as direct messaging, media transcoding, and recommendation algorithms, which are outside the scope of a database-focused project and can be listed as future enhancements.
2. System Requirements
2.1 Functional Requirements
Users can register, log in, and edit their profile.
Users can create, edit, and delete posts.
Users can comment on posts.
Users can like/unlike posts.
Users can follow/unfollow other users.
Users receive notifications for likes, comments, and new followers.
Users can view a personalized feed made up of posts from people they follow.
2.2 Non-Functional Requirements
Data integrity: no orphaned rows (e.g., a comment referencing a deleted post).
Performance: feed and like-count queries should remain fast as data grows, via indexing.
Consistency: like/follow counts must always match the underlying rows (enforced by triggers, not application code).

5. Normalization
Normalization removes redundancy and update anomalies by progressively splitting data into related tables. Below is the reasoning applied to this schema.
5.1 First Normal Form (1NF)
Every column holds a single atomic value — e.g., a post has one content field rather than a comma-separated list of hashtags, and there are no repeating groups (a user is never given post1, post2, post3 columns). All tables satisfy 1NF.
5.2 Second Normal Form (2NF)
2NF requires that non-key attributes depend on the whole primary key, which only matters for composite keys. In Likes (PK: user_id + post_id) and Follows (PK: follower_id + following_id), the only non-key column is created_at, which depends on the combination of both keys together — not on either key alone — so 2NF holds.
5.3 Third Normal Form (3NF)
3NF requires that non-key attributes depend only on the primary key, not on other non-key attributes (no transitive dependencies). For example, Posts does not store the author's username or email — those live only in Users and are retrieved via a join. This avoids the anomaly where changing a username would require updating every post row.
5.4 A Deliberate Denormalization
Posts.like_count is a deliberate exception: it duplicates information that could be derived with COUNT(*) FROM Likes WHERE post_id = ?. It is kept as a maintained column because feeds display like counts on every post, and recomputing that with a COUNT() on every read does not scale. A trigger (Section 8.1) keeps it consistent with the Likes table, so the denormalization never drifts out of sync.
6. Relational Schema (DDL)
The following CREATE TABLE statements implement the design above in standard SQL (MySQL/PostgreSQL compatible with minor type adjustments).
CREATE TABLE Users (
    user_id        INT AUTO_INCREMENT PRIMARY KEY,
    username       VARCHAR(30)  UNIQUE NOT NULL,
    email          VARCHAR(255) UNIQUE NOT NULL,
    password_hash  VARCHAR(255) NOT NULL,
    bio            TEXT,
    created_at     TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
 
CREATE TABLE Posts (
    post_id      INT AUTO_INCREMENT PRIMARY KEY,
    user_id      INT NOT NULL,
    content      VARCHAR(2200) NOT NULL,
    media_url    VARCHAR(500),
    like_count   INT DEFAULT 0,
    is_deleted   BOOLEAN DEFAULT FALSE,
    created_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (user_id) REFERENCES Users(user_id) ON DELETE CASCADE
);
 
CREATE TABLE Comments (
    comment_id   INT AUTO_INCREMENT PRIMARY KEY,
    post_id      INT NOT NULL,
    user_id      INT NOT NULL,
    content      VARCHAR(500) NOT NULL,
    created_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (post_id) REFERENCES Posts(post_id) ON DELETE CASCADE,
    FOREIGN KEY (user_id) REFERENCES Users(user_id) ON DELETE CASCADE
);
 
CREATE TABLE Likes (
    user_id      INT NOT NULL,
    post_id      INT NOT NULL,
    created_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (user_id, post_id),
    FOREIGN KEY (user_id) REFERENCES Users(user_id) ON DELETE CASCADE,
    FOREIGN KEY (post_id) REFERENCES Posts(post_id) ON DELETE CASCADE
);
 
CREATE TABLE Follows (
    follower_id   INT NOT NULL,
    following_id  INT NOT NULL,
    created_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (follower_id, following_id),
    FOREIGN KEY (follower_id)  REFERENCES Users(user_id) ON DELETE CASCADE,
    FOREIGN KEY (following_id) REFERENCES Users(user_id) ON DELETE CASCADE,
    CHECK (follower_id <> following_id)
);
 
CREATE TABLE Notifications (
    notification_id  INT AUTO_INCREMENT PRIMARY KEY,
    user_id          INT NOT NULL,
    type             VARCHAR(20) NOT NULL,
    reference_id     INT NOT NULL,
    is_read          BOOLEAN DEFAULT FALSE,
    created_at       TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (user_id) REFERENCES Users(user_id) ON DELETE CASCADE
);
7. Sample Queries
7.1 Personalized Feed
Posts from everyone a given user follows, most recent first.
SELECT p.post_id, u.username, p.content, p.like_count, p.created_at
FROM Posts p
JOIN Users u        ON u.user_id = p.user_id
JOIN Follows f      ON f.following_id = p.user_id
WHERE f.follower_id = ?
  AND p.is_deleted = FALSE
ORDER BY p.created_at DESC
LIMIT 20 OFFSET 0;
7.2 Top 10 Most-Liked Posts This Week
SELECT p.post_id, u.username, p.content, p.like_count
FROM Posts p
JOIN Users u ON u.user_id = p.user_id
WHERE p.created_at >= NOW() - INTERVAL 7 DAY
ORDER BY p.like_count DESC
LIMIT 10;
7.3 Suggested Users to Follow
Users followed by people you follow, excluding those you already follow and yourself — a classic 'friends of friends' self-join.
SELECT DISTINCT u.user_id, u.username
FROM Follows f1
JOIN Follows f2 ON f1.following_id = f2.follower_id
JOIN Users u    ON u.user_id = f2.following_id
WHERE f1.follower_id = ?          -- the current user
  AND f2.following_id <> ?        -- exclude self
  AND f2.following_id NOT IN (
        SELECT following_id FROM Follows WHERE follower_id = ?
  );
7.4 Mutual Followers of Two Users
SELECT u.username
FROM Follows f1
JOIN Follows f2 ON f1.follower_id = f2.follower_id
JOIN Users u    ON u.user_id = f1.follower_id
WHERE f1.following_id = ?   -- user A
  AND f2.following_id = ?;  -- user B
7.5 Engagement Summary per User
SELECT u.username,
       COUNT(DISTINCT p.post_id)  AS total_posts,
       COALESCE(SUM(p.like_count), 0) AS total_likes_received,
       COUNT(DISTINCT c.comment_id)   AS total_comments_written
FROM Users u
LEFT JOIN Posts p    ON p.user_id = u.user_id
LEFT JOIN Comments c ON c.user_id = u.user_id
GROUP BY u.user_id, u.username
ORDER BY total_likes_received DESC;
8. Triggers, Views & Stored Procedures
8.1 Trigger: Keep like_count in Sync
Rather than trusting the application layer to update the counter, the database enforces consistency itself.
DELIMITER $$
CREATE TRIGGER trg_like_insert
AFTER INSERT ON Likes
FOR EACH ROW
BEGIN
    UPDATE Posts SET like_count = like_count + 1
    WHERE post_id = NEW.post_id;
END$$
 
CREATE TRIGGER trg_like_delete
AFTER DELETE ON Likes
FOR EACH ROW
BEGIN
    UPDATE Posts SET like_count = like_count - 1
    WHERE post_id = OLD.post_id;
END$$
DELIMITER ;
8.2 Trigger: Auto-generate a Notification on Like
DELIMITER $$
CREATE TRIGGER trg_notify_on_like
AFTER INSERT ON Likes
FOR EACH ROW
BEGIN
    INSERT INTO Notifications (user_id, type, reference_id)
    SELECT p.user_id, 'like', NEW.post_id
    FROM Posts p
    WHERE p.post_id = NEW.post_id
      AND p.user_id <> NEW.user_id;   -- don't notify yourself
END$$
DELIMITER ;
8.3 View: User Feed
CREATE VIEW user_feed AS
SELECT f.follower_id AS viewer_id,
       p.post_id, p.content, p.like_count, p.created_at,
       u.username AS author
FROM Follows f
JOIN Posts p ON p.user_id = f.following_id
JOIN Users u ON u.user_id = p.user_id
WHERE p.is_deleted = FALSE;
 
-- Usage:
SELECT * FROM user_feed WHERE viewer_id = 7 ORDER BY created_at DESC;
8.4 Stored Procedure: Mutual Followers
DELIMITER $$
CREATE PROCEDURE get_mutual_followers(IN user_a INT, IN user_b INT)
BEGIN
    SELECT u.user_id, u.username
    FROM Follows f1
    JOIN Follows f2 ON f1.follower_id = f2.follower_id
    JOIN Users u    ON u.user_id = f1.follower_id
    WHERE f1.following_id = user_a
      AND f2.following_id = user_b;
END$$
DELIMITER ;
 
-- Usage:
CALL get_mutual_followers(3, 9);

11. Future Enhancements
Direct messaging between users (would need a Messages table with sender/receiver).
Hashtags and search (tag extraction + full-text index on Posts.content).
Media table separate from Posts to support multiple images/videos per post.
Basic recommendation logic using engagement history.
Partitioning Posts by date once data volume grows large enough to matter.
12. Conclusion
This project applies core DBMS concepts — ER modeling, normalization, constraints, triggers, views, stored procedures, and indexing — to a realistic, multi-relationship domain. The schema enforces integrity at the database layer rather than relying solely on application code, which is the central lesson the project is meant to demonstrate: a well-designed database should be correct and consistent even if the application code above it has bugs.
